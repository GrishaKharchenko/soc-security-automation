# Подготовка к собеседованию

Сводный документ по всему набору. В README каждого проекта есть свой раздел с
вопросами — здесь то, что касается набора целиком, плюс проверка готовности.

Подробный разбор кода: [`CODE_WALKTHROUGH.md`](CODE_WALKTHROUGH.md).

## Как представить проект за минуту

> Набор из трёх инструментов автоматизации SOC и оболочки, которая их
> объединяет. Первый анализирует индикаторы компрометации через VirusTotal,
> второй ищет атаки на учётные записи в логах аутентификации Linux и Windows,
> третий на Bash собирает DFIR-артефакты с подозреваемого хоста. Оболочка
> приводит их результаты к единому формату и связывает находки по общим
> сущностям: адрес, помеченный вредоносным в фиде, он же в логах как источник
> перебора паролей, он же в артефактах хоста — это одна атака, а не три
> независимых события.
>
> 357 тестов, вся сеть в тестах замокана, тестовые данные синтетические.
> Personal project — учебный, но по правилам рабочего кода: конфигурация в
> `.env`, логирование, обработка ошибок, осмысленные коды возврата.

**Чего не говорить:** «я сделал это с помощью ИИ» — как и «я написал это сам»,
если это не так. Правильная формулировка: «это мой учебный проект, я разбираюсь
в каждом решении и могу объяснить любую строку». И это должно быть правдой —
для того и написан `CODE_WALKTHROUGH.md`.

## Десять вопросов, которые зададут почти наверняка

### 1. «Почему 404 от VirusTotal — это не "чисто"?»

> 404 означает «в базе VT такого индикатора нет». Для домена,
> зарегистрированного вчера под фишинговую кампанию, это абсолютно ожидаемый
> ответ — и он скорее повод насторожиться, чем закрыть тикет. Поэтому в модели
> есть отдельный вердикт `UNKNOWN` с ненулевым risk score.
>
> Глубже: у меня разведены технический статус запроса (`EnrichmentStatus`) и
> аналитический вердикт (`Verdict`). «VT не ответил» и «VT ответил, что чисто» —
> принципиально разные вещи, и склеивать их значит прятать от аналитика
> реальный риск. На это есть отдельная группа тестов, которая проверяет, что
> ни один вид сбоя API не даёт вердикт `CLEAN`.

### 2. «Как вы работаете с rate limit?»

> Проактивно. У публичного ключа VT лимит 4 запроса в минуту, и систематическое
> превышение приводит к бану ключа, поэтому ловить 429 постфактум — плохая
> стратегия. Использую token bucket со скользящим окном на `deque`: храню метки
> времени последних N запросов и, если окно заполнено, жду ровно до момента,
> когда самый старый выпадет.
>
> Почему не `sleep(60/rpm)` после каждого запроса: это тормозит, когда запросов
> мало — попадания в кеш и неподдерживаемые типы всё равно получали бы паузу, —
> и не позволяет использовать разрешённый всплеск. Реактивная обработка 429
> тоже есть, как вторая линия обороны, с уважением к заголовку `Retry-After`.
>
> Использую `time.monotonic()`, а не `time.time()`: системные часы могут
> прыгнуть назад при синхронизации по NTP, и лимитер начал бы ждать час.

### 3. «Как работает обнаружение brute force?»

> Считаю неудачные попытки в скользящем окне с группировкой по паре
> «пользователь + адрес источника».
>
> Скользящее окно, а не фиксированные интервалы: атака на границе двух
> пятиминуток разделилась бы пополам и не превысила порог ни в одной.
>
> Пара как ключ: группировка только по пользователю смешивает забывчивого
> сотрудника с атакой, а только по адресу — превращает в brute force password
> spraying, у которого другая техника ATT&CK.
>
> Отдельно решаю проблему шума: 50 попыток подряд должны дать один алерт, а не
> сорок пять. Найденный всплеск поглощается целиком — это была реальная ошибка
> первой версии, я её увидел на тестовых данных.

### 4. «Чем password spraying отличается и зачем отдельное правило?»

> Политика блокировки считает неудачи по каждой учётной записи: пять промахов —
> блокировка. Атакующий, который это знает, берёт один популярный пароль и
> пробует его по сотне логинов. По каждому аккаунту две попытки, порог не
> превышен, детект перебора молчит.
>
> Он **принципиально** не может это увидеть, потому что смотрит на неудачи на
> пользователя, а надо смотреть на число пользователей на источник. Правило
> разворачивает ключ группировки и дополнительно требует, чтобы попыток на
> аккаунт было мало — иначе оно продублирует детект перебора.
>
> В тестах есть прямая проверка: на распылении правило AUTH-001 возвращает
> пустой список, а AUTH-003 срабатывает.

### 5. «Почему выбрана именно эта техника ATT&CK?»

> У каждой техники в `mitre.py` есть поле `rationale` — какое именно
> наблюдаемое поведение ей соответствует и чем она отличается от соседней.
>
> Пример: перебор **несуществующих** логинов я отношу к T1087 Account Discovery,
> а не к T1110 Brute Force. Цель здесь не подобрать пароль, а выяснить, какие
> учётные записи существуют — система отвечает на валидный и невалидный логин
> по-разному. Это разведка перед атакой, тактика Discovery, а не Credential
> Access.
>
> Второй пример: успешный вход после серии неудач — T1078 Valid Accounts. Сам
> по себе успешный вход техникой не является; значение придаёт контекст, потому
> что с этого момента действия атакующего неотличимы от действий легитимного
> пользователя.
>
> И то, чего я намеренно **не** делаю: не приписываю техники индикаторам.
> Вредоносный хеш не соответствует никакой технике — техника описывает
> поведение, а не артефакт.

### 6. «Как связываются события между собой?»

> На двух уровнях.
>
> Внутри Log Analyzer одна атака даёт несколько срабатываний: разведка, перебор,
> успех, sudo. Я связываю их по общей сущности — прежде всего по адресу
> источника, при его отсутствии по учётной записи — и собираю в инцидент с
> максимальной severity и объединённым списком техник.
>
> На уровне оболочки связываются находки **разных инструментов** по общим
> сущностям. Ключевой признак — подтверждение из нескольких независимых
> источников: оно повышает критичность на один уровень, но не выше HIGH, чтобы
> не обесценить CRITICAL.
>
> Ограничение честно описано в README: если атакующий сменил адрес после входа,
> инцидент распадётся на два. Правильное решение — граф связей сущностей, так
> устроены промышленные корреляторы; для учебного проекта я счёл это избыточным.

### 7. «Как вы боретесь с ложными срабатываниями?»

> Четыре способа.
>
> Первый — пороги в конфигурации, а не в коде: у разных команд разная
> толерантность.
>
> Второй — разделение severity и confidence. Это разные оси: вход в три часа
> ночи потенциально критичен по последствиям, но уверенность в нём низкая.
> Смешивание их в один показатель теряет информацию, нужную для приоритизации.
>
> Третий — контекст. В тестовых данных я держу контрпримеры, и первый же прогон
> показал, что сотрудник, трижды ошибшийся паролем на своём рабочем месте,
> получает `CRITICAL`. Добавил проверку, входила ли учётная запись с этого
> адреса раньше: знакомый адрес понижает находку до `MEDIUM`.
>
> Четвёртый — слабые сигналы остаются слабыми. Вход вне рабочего времени имеет
> `LOW` и низкую уверенность; его задача не поднять тревогу, а добавить веса
> инциденту при корреляции.

### 8. «Как вы тестировали то, что зависит от внешнего API?»

> Через `requests-mock` с инъекцией сессии в клиент. Реальная сеть в тестах —
> это флаки, зависимость от квоты и невозможность воспроизвести редкие ответы.
> С моками я проверяю сценарии, которые в проде ловятся раз в месяц и всегда не
> вовремя: 429 с `Retry-After`, серия 5xx с последующим успехом, обрыв
> соединения, HTML вместо JSON, пустой ответ без полей.
>
> Но моков недостаточно, и я это проверил на практике. Первый прогон по живому
> VirusTotal нашёл три вещи, которых в моках не было: 400 вместо 404 на
> зарезервированных доменных зонах, двойной расход квоты на MD5 и SHA256 одного
> файла, и положительная репутация +3788 у EICAR — потому что `reputation` в VT
> это голоса сообщества, а не оценка вредоносности. Если бы скоринг строился на
> репутации, EICAR получил бы вердикт «чисто».
>
> Все три починил и закрыл тестами. Вывод: моки дают скорость и
> воспроизводимость, живой прогон даёт реальность, нужны оба.

### 9. «Что вы соберёте при триаже, если у вас нет root?»

> Процессы, свои сессии, сетевые соединения без привязки к процессам,
> `/etc/passwd`, свой crontab, конфигурацию SSH, содержимое доступных на чтение
> домашних каталогов. Не соберу: `/etc/shadow`, чужие crontab, `lastb`, журналы
> аутентификации, правила firewall.
>
> Принципиально, что скрипт **помечает недоступное явно** — «НЕТ ПРАВ НА
> ЧТЕНИЕ (требуется root)», а не выдаёт пустой файл. Пустой отчёт, означающий
> «мы не смогли посмотреть», нельзя путать с «мы посмотрели и ничего не нашли».
>
> И порядок сбора: сначала летучее — процессы, соединения, сессии, — потом то,
> что лежит на диске. Это принцип убывающей летучести из RFC 3227. Если начать
> с поиска SUID-файлов по всей файловой системе, процесс атакующего может
> успеть завершиться.

### 10. «Как убедиться, что скрипт триажа ничего не сломает?»

> Четыре аргумента.
>
> В нём нет ни одной изменяющей команды: только чтение, `find`, `ps`, `cat`.
>
> Единственная запись — в каталог результатов, который задаётся аргументом.
>
> В тестах есть проверка-канарейка: создаётся временный файл, считается хеш,
> прогоняется скрипт, хеш сверяется. Утверждение из документации подтверждено
> тестом, а не словом автора.
>
> И рекомендация в README: запускать с внешнего носителя, результаты писать вне
> исследуемого хоста, не перезагружать до сбора.
>
> Почему это важно: изменяя систему во время реагирования, вы уничтожаете
> доказательства — после этого любое ваше действие невозможно отличить от
> действий атакующего.

## Вопросы, которые могут застать врасплох

### «Почему в скрипте не `set -e`?»

> Потому что для инструмента реагирования это неверно. `set -e` прерывает
> скрипт на первой ошибке, а задача триажа — собрать максимум доступного. Если
> на хосте нет `ss` или недоступен `/var/log/secure`, это не повод потерять все
> остальные артефакты. Использую `set -uo pipefail`, а ошибки обрабатываю явно,
> каждой командой, с записью в артефакт и в журнал.

### «Зачем машиночитаемый вывод у Bash-скрипта?»

> Текст читает человек, JSON читает машина. Скрипт — часть набора, и его
> результаты подхватывает единая оболочка, которая сводит находки трёх
> инструментов в общий отчёт. Без машиночитаемого формата такая интеграция
> невозможна, и скрипт остался бы вещью в себе.
>
> Второе следствие: на Windows Bash-скрипт не запускается, но оболочка
> импортирует готовый `findings.json`, собранный в WSL или на другом хосте — и
> кросс-корреляция работает полностью.

### «Что будет, если один модуль оболочки упадёт?»

> Прогон продолжится. Каждый модуль вызывается через обёртку, которая ловит и
> известные ошибки адаптера, и любое непредвиденное исключение: модули
> разрабатывались независимо, и оболочка не может знать полный перечень их
> ошибок. Сбой попадает в список `failed_modules` в отчёте и в stderr.
>
> Важная деталь: код возврата не может быть нулевым при частичном сбое, иначе
> неполный результат выглядел бы как чистый. На это есть тест.

### «Почему у ошибки в аргументах код 3, а не 2?»

> Потому что код 2 в моём контракте занят: «есть критические находки» у двух
> инструментов и «часть индикаторов проверить не удалось» у третьего. `argparse`
> по умолчанию отдаёт 2 при ошибке в аргументах, и пайплайн, проверяющий
> `$? -eq 2`, принял бы опечатку в команде за результат анализа.
>
> Я это нашёл при систематической проверке CLI, переопределил метод `error()` в
> подклассе `ArgumentParser` во всех трёх инструментах и добавил регрессионные
> тесты.

### «Расскажите про самую сложную ошибку, которую нашли»

> Каталог с библиотеками Bash-скрипта не попал в репозиторий. Стандартный
> Python-шаблон `.gitignore` содержит правило `lib/` — оно предназначено для
> виртуальных окружений, но поглотило `projects/linux-triage/lib/` с тремя
> файлами.
>
> Локально ошибка не проявлялась никак: файлы лежали в рабочем каталоге, тесты
> проходили, скрипт работал. На чистом клоне скрипт не запускался вовсе, и 33
> теста из 44 падали.
>
> Нашёл этап проверки на чистой копии — я специально включил его в план
> проверки именно для такого класса проблем: репозиторий, который работает
> только на машине автора. Теперь клонирую в пустой каталог и прогоняю всё
> заново после любого изменения `.gitignore`.

### «Почему во всех трёх проектах почти одинаковые `config.py` и `logging_setup.py`?»

> Осознанное решение. Благодаря нему четвёртый проект стал объединением, а не
> переписыванием: модули говорили на одном языке ещё до того, как их связали.
>
> Общий модуль я намеренно не выделял заранее — по правилу «дублирование
> терпимо до третьего раза». Пока не написаны все три инструмента, неизвестно,
> какая именно часть окажется общей, и абстракция, построенная на одном примере,
> почти всегда неверна. Сейчас, когда видно, что общего, вынести ядро было бы
> правильным следующим шагом — и это первый пункт в моём списке «что сделал бы
> иначе».

### «Что бы вы улучшили?»

>
> Заставил бы Bash-скрипт заполнять структурированное поле `entities` вместо

> формулировок и сломается при их изменении.
>
> Заменил бы корреляцию по точному совпадению на граф сущностей с учётом
> подсетей и временной близости.
>
> Добавил бы базовую линию поведения, хранимую отдельно от анализируемых логов:
> правило «новый источник» на одном суточном файле даёт слабый сигнал.
>
> Вынес бы общий код в пакет ядра.

## Демонстрация: последовательность на 5 минут

Проверено на чистом клоне. Подробности — в [`LOCAL_SETUP.md`](LOCAL_SETUP.md).

**1. Разбор индикаторов, 20 секунд, сеть не нужна**

```bash
cd projects/ioc-analyzer
python -m ioc_analyzer classify -i data/sample_iocs.txt
```

Показать: `evil.test` со счётчиком 2 (схлопнулись `EVIL.TEST.` и `evil[.]test`),
пометки `[defanged]`, punycode вместо `мой-сайт.рф`.

**2. Обнаружение атак в логах, 20 секунд**

```bash
cd ../log-analyzer
python -m log_analyzer analyze -i data/auth.log data/windows_security.csv --year 2026
```

Показать: инциденты объединяют по несколько находок, у каждой техники ATT&CK,
`AUTH-003` поймал spraying.

**3. Справочник правил**

```bash
python -m log_analyzer rules
```

**4. Объединение — главное**

```bash
cd ../soc-toolkit
python -m soc_toolkit run \
    --iocs samples/incident_iocs.txt --offline --include-clean \
    --logs ../log-analyzer/data/auth.log --year 2026 \
    --triage-report ../linux-triage/samples/findings.json
```

Показать блок «ПОДТВЕРЖДЕНО НЕСКОЛЬКИМИ ИНСТРУМЕНТАМИ»: адрес `192.0.2.66`
найден независимо всеми тремя инструментами.

## Проверка готовности

Отметьте, что можете объяснить без подсказки:

- [ ] почему 404 не равно «чисто» и как это выражено в коде
- [ ] почему rate limiter проактивный и почему `monotonic`, а не `time`
- [ ] как работает скользящее окно и какие две ошибки оно предотвращает
- [ ] почему spraying требует отдельного правила
- [ ] почему перебор несуществующих логинов — это T1087, а не T1110
- [ ] чем severity отличается от confidence и зачем их разделять
- [ ] что такое принцип убывающей летучести и почему он определяет порядок сбора
- [ ] почему в `authorized_keys` смотрят при расследовании
- [ ] что делает `/etc/ld.so.preload` и почему его наличие критично
- [ ] почему в скрипте триажа нет `set -e`
- [ ] что показал живой прогон по VirusTotal, чего не показали моки
- [ ] какие компромиссы есть в архитектуре и почему они приняты

Если по какому-то пункту ответа нет — соответствующий раздел в
[`CODE_WALKTHROUGH.md`](CODE_WALKTHROUGH.md).
