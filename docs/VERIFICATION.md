# План проверки набора

Документ описывает, **как проверялось** всё, что есть в репозитории, и
фиксирует результаты последнего прогона. Он нужен по двум причинам: чтобы
проверку можно было воспроизвести, и чтобы на собеседовании было что ответить
на вопрос «а как вы убедились, что это работает».

Принцип: проверка идёт от дешёвого к дорогому. Сначала то, что ловит ошибки
за секунды (синтаксис, импорты), потом тесты, потом реальные запуски, и в
конце — проверка на чистой копии репозитория, которая ловит скрытые
зависимости от окружения разработчика.

| # | Что проверяется | Как | Почему важно |
|---|---|---|---|
| 1.1 | Синтаксис всех модулей Python | `python -m compileall` | Опечатка в редко исполняемой ветке иначе всплывёт у пользователя |
| 1.2 | Синтаксис всех скриптов Bash | `bash -n` | То же самое, но для скриптов, где нет импорта |
| 1.3 | Импортируемость всех модулей | импорт каждого модуля пакета | Циклические импорты и опечатки в именах |
| 1.4 | Отсутствие отладочного мусора | поиск `print(` вне CLI, `TODO`, `FIXME`, `XXX` | Отладочная печать в библиотечном коде ломает вывод |
| 1.5 | Отсутствие посторонних символов | поиск иероглифов и мусора в исходниках | Следы автогенерации выглядят неряшливо |
| 1.6 | Единый стиль кодировки | все файлы читаются как UTF-8 | Смешанные кодировки ломают сборку у другого человека |

## Этап 6. Проверка на чистой копии

Самый важный и самый часто пропускаемый этап. Репозиторий клонируется в
пустой каталог, ставятся зависимости, прогоняются тесты и запуски. Это ловит
скрытые зависимости от окружения разработчика: несохранённый файл, забытый в
`.gitignore` артефакт, путь, работающий только на одной машине.

| # | Что проверяется |
|---|---|
| 6.1 | Клон содержит все файлы, нужные для запуска |
| 6.2 | Тесты проходят на чистой копии |
| 6.3 | Демонстрационные команды из README работают |
| 6.4 | Тестовые данные (логи, фиды, отчёт триажа) присутствуют |

## Этап 7. Достоверность документации

### Что нашла проверка

**Этап 3 — коды возврата при ошибке в аргументах.**
Неверный аргумент во всех трёх Python-инструментах завершал процесс кодом 2,
потому что таково поведение `argparse` по умолчанию. Но код 2 в контракте уже
занят: «часть индикаторов проверить не удалось» у IOC Analyzer и «есть
критические находки» у остальных. Пайплайн, проверяющий `$? -eq 2`, принял бы
опечатку в команде за результат анализа.

*Исправление:* все парсеры переведены на подкласс `ArgumentParser`, который
отдаёт код 3, отведённый под ошибки запуска. Добавлены регрессионные тесты в
каждый проект.

**Этап 6 — библиотеки Bash-скрипта не попали в репозиторий.**
Самая серьёзная находка. Каталог `projects/linux-triage/lib/` с тремя файлами
отсутствовал в клоне: стандартный Python-шаблон `.gitignore` содержит правило
`lib/` для виртуальных окружений, и оно поглотило библиотеки Bash-инструмента.
На чистой копии скрипт не запускался вовсе, 33 теста из 44 падали.

Локально ошибка не проявлялась никак: файлы лежали в рабочем каталоге, всё
работало. Это ровно тот класс проблем, ради которого этап проверки на чистой
копии и существует, — репозиторий, работающий только на машине автора.

*Исправление:* правила-исключения в `.gitignore`, файлы закоммичены.
Повторный прогон на новом клоне: 357 тестов пройдено, скрипт работает.

**Этап 7 — расхождения в документации.**
Числа тестов в README отстали от фактических после добавления регрессионных
тестов (168/91/48 против 170/93/50). Ссылка на `docs/LOCAL_SETUP.md` вела в
несуществующий файл.

*Исправление:* числа актуализированы, документ написан.

## Как повторить проверку

```bash
# этап 2 — тесты
for p in ioc-analyzer log-analyzer soc-toolkit; do
    (cd projects/$p && python -m pytest)
done
(cd projects/linux-triage && bash tests/run_tests.sh)

# этап 6 — чистая копия (главный этап)
git clone --branch claude/ioc-analyzer-soc-98gwly . /tmp/clean-check
cd /tmp/clean-check && for p in ioc-analyzer log-analyzer soc-toolkit; do
    (cd projects/$p && python -m pytest)
done
```

Этап 6 стоит повторять после каждого изменения в `.gitignore` и после
добавления любых новых каталогов: именно там прячутся ошибки, невидимые
локально.
