# IOC Analyzer

> Модуль репозитория [soc-security-automation](../../README.md) · Python · автономный проект

Инструмент автоматизированного анализа индикаторов компрометации (IOC) для SOC.
Принимает «грязный» фид в TXT/CSV, определяет тип каждого индикатора,
нормализует и дедуплицирует данные, обогащает их через VirusTotal API v3,
рассчитывает объяснимый вердикт и сохраняет отчёты в JSON и CSV.

> **Безопасность тестовых данных.** В репозитории нет реальных вредоносных
> индикаторов. Примеры используют IP из RFC 5737/3849 и домены из RFC 2606/6761
> (зарезервированы для документации), хеши пустого файла и хеш EICAR —
> официального безвредного тест-файла антивирусной индустрии.

---

## Возможности

| # | Функция | Где реализовано |
|---|---|---|
| 1 | Чтение TXT и CSV (автоопределение кодировки и разделителя) | `parsers/reader.py` |
| 2 | Определение типа: IPv4, IPv6, domain, URL, MD5, SHA1, SHA256 | `ioc/detector.py` |
| 3 | Нормализация, refang и дедупликация со счётчиком повторов | `ioc/normalizer.py` |
| 4 | Обогащение через VirusTotal API v3 | `enrichment/virustotal.py` |
| 5 | Обработка 429/401/404/5xx, таймаутов, ретраи с backoff | `enrichment/virustotal.py`, `enrichment/rate_limiter.py` |
| 6 | Расчёт вердикта и risk score с объяснением | `scoring/verdict.py` |
| 7 | Отчёты в JSON и CSV + сводка в консоль | `reporting/writers.py` |
| 8 | CLI с подкомандами и осмысленными кодами возврата | `cli.py` |
| 9 | Логирование в консоль и файл с ротацией, маскирование секретов | `logging_setup.py` |
| 10 | Конфигурация через `.env` с переопределением флагами CLI | `config.py` |

Дополнительно: кеш ответов с TTL (экономия квоты API), фильтр по типам IOC,
режим `--offline` (работа без сети), режим `classify` (проверка разбора фида).

### Принципы, заложенные в архитектуру

**Разделение ответственности.** Каждый модуль решает одну задачу и не знает о
соседях больше необходимого. `reader` ничего не знает о VirusTotal, `verdict`
не знает о формате отчётов, `writers` не знают, откуда взялись данные.

**Инверсия зависимостей.** Скоринг и отчёты зависят от внутренней модели
`EnrichmentResult`, а не от формата ответа вендора. Подключение AbuseIPDB или
MISP — это один новый класс, наследник `EnrichmentProvider`; остальной код
не меняется.

**Конфигурация вместо констант.** Пороги вердикта, лимиты и таймауты живут
в `.env`. У разных команд разная толерантность к false positive, и менять её
правкой исходников — плохая идея.

**Отказоустойчивость по умолчанию.** `enrich()` по контракту не выбрасывает
исключений: любая проблема становится результатом со статусом. Прогон из 500
индикаторов не падает из-за одного таймаута на 47-м.

**Тонкий CLI.** Логика живёт в `IOCAnalyzer`, а не в обработчиках argparse.
Тот же конвейер вызывается из SOAR, Airflow или веб-сервиса без переписывания.

## Логика вердикта

| Условие | Вердикт | Score |
|---|---|---|
| детектов ≥ `VERDICT_MALICIOUS_THRESHOLD` (по умолчанию 3) | `MALICIOUS` | ≥ 60 |
| детектов 1–2, либо `suspicious` ≥ порога, либо репутация ниже пола | `SUSPICIOUS` | ≥ 30 |
| детектов нет, репутация в норме | `CLEAN` | 0–~10 |
| VirusTotal не знает индикатор (HTTP 404) | `UNKNOWN` | 25 |
| обогащение не удалось (сеть, лимит, 401, 5xx) | `ERROR` | 20 |
| провайдер отверг индикатор (HTTP 400/422), зарезервированная зона DNS, приватный адрес, `--offline` | `SKIPPED` | 0 |

Три принципа, которые здесь важнее формул:

1. **Один детект — ещё не приговор.** Один сработавший движок из 70 почти
   всегда false positive (эвристика, PUA, упаковщик). Отсюда порог в 3 детекта
   и отдельный вердикт `SUSPICIOUS` для пограничных случаев.
2. **Отсутствие данных — это не «чисто».** `ERROR` и `UNKNOWN` существуют
   именно поэтому. Индикатор, который не удалось проверить, должен попасть
   к аналитику, а не раствориться среди безопасных.
3. **Вердикт обязан быть объясним.** В `reasons` пишется, почему принято
   именно такое решение. Инструмент, чьи выводы нельзя проверить, аналитик
   перестанет использовать — и будет прав.

`risk_score` (0–100) отвечает не на вопрос «что это», а на вопрос «в каком
порядке разбирать»: 5/70 и 55/70 дают один вердикт, но очень разный приоритет.

## Что изменил прогон по живому API

Модульные тесты покрывают сценарии, которые я предусмотрел. Первый же запуск
по настоящему VirusTotal нашёл три вещи, которых в этом списке не было.

**1. HTTP 400 вместо ожидаемого 404.** На домены в зонах `.test` и `.example`
VirusTotal отвечает не «не нашёл», а `400 not a valid domain pattern` — эти
зоны зарезервированы RFC 2606 и в корне публичного DNS не существуют, искать
их негде. Изначально код относил 400 к `API_ERROR`, то есть к вердикту `ERROR`
с пометкой «требуется ручная проверка». Это неверно: аналитик, открыв VT
руками, получит тот же отказ. Теперь 400/422 дают статус `UNSUPPORTED` и
вердикт `SKIPPED` — «проверить нельзя в принципе», а не «проверить не вышло».

**2. Бесполезные запросы можно не делать вовсе.** Раз зарезервированные зоны
непроверяемы, отсеивать их надо *до* обращения к API. То же касается приватных
и служебных адресов: `10.0.0.5` из внутреннего лога SIEM попадает в фид
регулярно, но внешнему Threat Intelligence о нём сказать нечего. Модуль
`ioc/scope.py` отсекает такие индикаторы заранее, экономя суточную квоту и
не засоряя отчёт. Важная тонкость: документационные диапазоны RFC 5737
(`192.0.2.0/24` и соседние) в этот фильтр намеренно **не** попали — стандартный
`ipaddress.is_private` считает их приватными, но VirusTotal их принимает и
отдаёт данные, что и показал живой запрос.

**3. Один файл — два запроса.** Фид содержал MD5 и SHA256 одного образца
(EICAR). Дедупликация их не свела: вывести SHA256 из MD5 невозможно. Ответ VT
при этом содержит все три хеша файла в `attributes` — теперь результат
кешируется под каждым из них, и второй хеш того же файла берётся из кеша.

Общий вывод, который стоит проговорить на собеседовании: моки проверяют
известные сценарии, а неизвестные находит только живой прогон. Оба вида
тестирования нужны, и ни один не заменяет другой.

## Конфигурация

Все параметры — в `.env` (шаблон: `.env.example`). Приоритет источников:

```
значения по умолчанию → .env → переменные окружения → флаги CLI
```

Ключевые параметры:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `VT_API_KEY` | — | ключ VirusTotal API v3 |
| `VT_REQUESTS_PER_MINUTE` | `4` | лимит публичного ключа VT |
| `VT_MAX_RETRIES` | `3` | повторы при 429/5xx/таймаутах |
| `VT_BACKOFF_FACTOR` | `2.0` | пауза `factor × 2^попытка` |
| `VERDICT_MALICIOUS_THRESHOLD` | `3` | детектов для вердикта `MALICIOUS` |
| `VERDICT_REPUTATION_FLOOR` | `-20` | репутация, ниже которой IOC подозрителен |
| `CACHE_ENABLED` / `CACHE_TTL` | `true` / `86400` | кеш ответов VT |
| `LOG_LEVEL` / `LOG_FILE` | `INFO` / `logs/…` | логирование |

`.env` добавлен в `.gitignore` — ключ не должен попасть в репозиторий.

## Что рассказать на собеседовании

Ниже — вопросы, которые реально задают по такому проекту, и содержательные
ответы на них.

### 1. «Расскажите про проект за минуту»

> Инструмент автоматизации первичного триажа IOC. На входе — фид из TXT или
> CSV, на выходе — отчёт с вердиктом по каждому индикатору. Внутри четыре
> этапа: разбор и нормализация, обогащение через VirusTotal, скоринг,
> формирование отчётов. Сделан модульно: провайдер обогащения абстрагирован,
> пороги вынесены в конфигурацию, CLI — тонкий слой над библиотечным кодом,
> так что тот же конвейер вызывается из SOAR или планировщика. 168 тестов,
> сеть в тестах замокана полностью.

### 2. «Почему 404 от VirusTotal — это не "чисто"?»

Главный вопрос про понимание предметной области, а не про Python.

> 404 означает «в базе VT такого индикатора нет». Для домена, зарегистрированного
> вчера под фишинговую кампанию, это абсолютно ожидаемый ответ — и он скорее
> повод насторожиться, чем закрыть тикет. Поэтому в модели есть отдельный
> вердикт `UNKNOWN` с ненулевым risk score. Точно так же разведены статус
> запроса (`EnrichmentStatus`) и вердикт (`Verdict`): «VT не ответил» и
> «VT ответил, что чисто» — принципиально разные вещи, и склеивать их —
> значит прятать от аналитика реальный риск.

### 3. «Как вы работаете с rate limit?»

> Проактивно. У публичного ключа VT лимит 4 запроса в минуту, и систематическое
> превышение приводит к бану ключа, поэтому ловить 429 постфактум — плохая
> стратегия. Я использую token bucket со скользящим окном на `deque`: храню
> метки времени последних N запросов и, если окно заполнено, жду ровно до
> момента, когда самый старый запрос из него выпадет. Это точнее, чем
> `sleep(60/rpm)` после каждого запроса: не тормозит, когда запросов мало, и
> позволяет использовать разрешённый всплеск. Реактивная обработка 429 тоже
> есть — как вторая линия обороны, с уважением к заголовку `Retry-After`.
> Плюс кеш с TTL: повторный прогон того же фида не тратит суточную квоту.

### 4. «Какие ошибки API вы обрабатываете и чем они отличаются?»

> Ключевая мысль: разные ошибки требуют разной реакции, и `except Exception:
> pass` — это антипаттерн, который превращает сбой в тихое «всё хорошо».
> - **404** — не ошибка, а валидный ответ: `NOT_FOUND`, без ретраев.
> - **401/403** — проблема с ключом, ретраи бессмысленны, выходим сразу.
> - **429** — ждём `Retry-After` или экспоненциальный backoff и повторяем.
> - **5xx, таймауты, обрывы** — временные сбои, экспоненциальный backoff.
> - **400/422** — некорректный запрос, повтор даст тот же результат.
>
> И контракт уровнем выше: метод `enrich()` не выбрасывает исключений вообще.
> Прогон из 500 индикаторов не имеет права упасть целиком из-за одного таймаута.

### 5. «Зачем нужна нормализация, если можно просто отправить строку в API?»

> Один индикатор приезжает из разных источников в разном виде:
> `HXXP://Evil[.]Test/Login` из письма, `evil.test` из SIEM, `EVIL.TEST.` из
> выгрузки. Без канонизации мы трижды сожжём квоту API и трижды покажем
> аналитику одно и то же. Отдельно стоит упомянуть refang: defanged-запись —
> индустриальный стандарт передачи IOC в тикетах и почте, чтобы никто не
> кликнул случайно, и инструмент обязан её понимать. Ещё пара неочевидных
> моментов: IDN-домены надо приводить к punycode, потому что именно так их
> знает VT, а путь в URL нормализовать по регистру **нельзя** — `/Login` и
> `/login` могут быть разными ресурсами.

### 6. «Как считается вердикт и почему именно так?»

> Порог по количеству детектов, а не «хотя бы один движок». Один сработавший
> антивирус из 70 — почти всегда false positive: эвристика, PUA, подозрительный
> упаковщик. Если по одному детекту поднимать инцидент, SOC утонет в шуме и
> начнёт игнорировать инструмент. Поэтому по умолчанию 3 детекта — `MALICIOUS`,
> 1–2 — `SUSPICIOUS` с явной пометкой о возможном FP. Пороги вынесены в `.env`,
> потому что у разных команд разная толерантность к ложным срабатываниям.
> Отдельно считается risk score 0–100 — он отвечает не «что это», а «в каком
> порядке разбирать». И каждый вердикт сопровождается списком причин: вывод,
> который нельзя проверить, доверия не заслуживает.

### 7. «Как тестировали то, что зависит от внешнего API?»

> Через `requests-mock` с инъекцией сессии в клиент. Реальная сеть в тестах —
> это флаки, зависимость от квоты и невозможность воспроизвести редкие ответы.
> С моками я проверяю ровно те сценарии, которые в проде ловятся раз в месяц и
> всегда не вовремя: 429 с `Retry-After`, серия 5xx с последующим успехом,
> обрыв соединения, HTML вместо JSON, пустой ответ без полей. Отдельный класс
> тестов — на инварианты: «сбой API никогда не даёт вердикт CLEAN» и «`enrich()`
> не выбрасывает исключений».

### 8. «Вы тестировали только на моках. Этого достаточно?»

> Нет, и я это проверил на практике. Моки покрывают сценарии, которые я
> предусмотрел: 429, 5xx, таймауты, битый JSON. Первый прогон по живому
> VirusTotal нашёл три вещи, которых в этом списке не было: 400 вместо 404 на
> зарезервированных доменных зонах, бессмысленные запросы по приватным адресам
> и двойной расход квоты на MD5 и SHA256 одного файла. Все три я починил и
> закрыл тестами — теперь они часть регрессии. Вывод простой: моки дают
> скорость и воспроизводимость, живой прогон даёт реальность, и нужны оба.

### 9. «Что бы вы добавили дальше?»

> - Несколько провайдеров (AbuseIPDB, OTX, внутренний MISP) с агрегацией
>   вердиктов — абстракция `EnrichmentProvider` для этого уже готова.
> - Асинхронность (`asyncio` + `aiohttp`) для премиум-ключа с высоким лимитом;
>   при публичном ключе смысла нет — упрёмся в rate limit, а не в сеть.
> - Whitelist собственной инфраструктуры и популярных доменов: не тратить
>   квоту на `google.com` и не пугать аналитика своими же адресами.
> - Выгрузка результатов прямо в TheHive/MISP и запуск по расписанию.
> - Обогащение через pDNS и WHOIS: возраст домена — сильный сигнал, свежая
>   регистрация часто важнее числа детектов.
