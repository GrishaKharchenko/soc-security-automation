# Linux Incident Triage

> Модуль репозитория [soc-security-automation](../../README.md) · Bash · автономный проект

Скрипт первичного сбора DFIR-артефактов с Linux-хоста, на котором подозревается
компрометация. Собирает 45+ артефактов, прогоняет по ним восемь групп проверок
и выдаёт результат в двух видах: человекочитаемая сводка и машиночитаемый
`findings.json`.

---

## Гарантии безопасности

**Скрипт работает только на чтение.** Он не изменяет и не удаляет файлы на
исследуемой системе, не останавливает процессы, не правит конфигурацию, не
содержит эксплойтов и деструктивных команд. Единственная запись — в каталог
результатов, который задаётся аргументом.

Это не формальность. Изменяя систему во время реагирования, вы уничтожаете
доказательства: после этого любое ваше действие невозможно отличить от
действий атакующего, и материалы теряют ценность для расследования. В тестах
есть прямая проверка — файл-канарейка не должен измениться после прогона.

**Работает без root**, но часть артефактов будет недоступна (`/etc/shadow`,
чужие crontab, журналы аутентификации, правила firewall). Недоступное
помечается в отчёте явно:

```
### /etc/shadow — НЕТ ПРАВ НА ЧТЕНИЕ (требуется root)
```

Разница между «данных нет» и «данные не собрали» принципиальна: пустой файл,
выданный за отсутствие находок, — это ложное чувство безопасности.

**Хеши паролей не выгружаются.** Из `/etc/shadow` берутся только метаданные:
у кого пустой пароль, когда пароль менялся. Копирование хешей создало бы
новый носитель секретов, а для триажа они не нужны.

## Установка и запуск

```bash
cd projects/linux-triage
chmod +x triage.sh

sudo ./triage.sh                    # полный сбор в текущий каталог
sudo ./triage.sh -o /mnt/usb        # результат на внешний носитель
./triage.sh --no-archive -q         # без root, без архива, без вывода
bash tests/run_tests.sh             # 44 теста
```

| Параметр | Назначение |
|---|---|
| `-o, --output КАТАЛОГ` | куда сохранить результаты |
| `--no-archive` | не упаковывать в `tar.gz` |
| `-q, --quiet` | не выводить ход работы |
| `-h, --help` | справка |
| `-V, --version` | версия |

| Код возврата | Значение |
|---|---|
| 0 | сбор выполнен, подозрительного не найдено |
| 1 | есть находки |
| 2 | есть **критические** находки |
| 3 | ошибка запуска |

**На Windows скрипт не работает** — нужен Linux или WSL
(`wsl --install` в PowerShell от администратора).

### Как правильно применять

1. Запускать **с внешнего носителя**, а не копировать скрипт на исследуемый хост.
2. Результаты писать **вне исследуемой системы** (`-o /mnt/usb`).
3. Не перезагружать и не выключать хост до сбора: список процессов, сетевые
   соединения и активные сессии исчезнут безвозвратно.
4. Сохранить `MANIFEST.sha256` — он подтверждает, что артефакты не менялись
   после сбора.

## Что собирается и зачем

Порядок сбора соответствует **принципу убывающей летучести** (RFC 3227, Order
of Volatility): сначала то, что исчезнет при первом изменении состояния
системы, потом то, что лежит на диске.

### 1. Система

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `01_system_info.txt` | hostname, ядро, дистрибутив, время, часовой пояс | Привязка находок к конкретному хосту. Часовой пояс критичен: без него временная шкала инцидента собирается неверно |
| `01_uptime.txt` | время работы, средняя нагрузка | Недавняя перезагрузка может означать установку модуля ядра или заметание следов. Аномальная нагрузка — майнер |
| `01_kernel_modules.txt` | загруженные модули ядра | Руткит уровня ядра виден здесь как незнакомый модуль |

### 2. Пользователи и сессии

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `02_who.txt`, `02_w.txt` | кто в системе **прямо сейчас** | Самый летучий артефакт. Если атакующий активен, здесь его сессия и адрес |
| `02_last.txt` | история входов | Временная шкала доступа: когда и откуда входили |
| `02_lastlog.txt` | последний вход **каждой** учётной записи | Вход под сервисной учётной записью, которая по замыслу не должна логиниться, — сильный признак компрометации |
| `02_lastb.txt` | неудачные попытки входа | Перебор паролей. Требует root |

### 3. Процессы

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `03_ps_full.txt` | полное дерево процессов | Дерево, а не список: важно, кто чей родитель. `sshd → bash → nc` — это цепочка атаки |
| `03_ps_sorted_cpu.txt` | по загрузке CPU | Майнеры и брутфорсеры видны сразу |
| `03_process_binaries.txt` | соответствие PID → исполняемый файл | **Ключевой артефакт.** Пометка `(deleted)` означает, что бинарник удалён с диска при работающем процессе — классический приём сокрытия |

### 4. Сеть

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `04_listening.txt` | слушающие сокеты с процессами | Что принимает соединения извне. Незнакомый порт = бэкдор или средство удалённого управления |
| `04_connections.txt` | активные соединения | **Куда хост ходит сам.** Исходящее соединение на неизвестный адрес — канал управления (C2) или выгрузка данных |
| `04_routes.txt`, `04_addresses.txt` | маршруты и интерфейсы | Добавленный маршрут или туннельный интерфейс — признак сетевого закрепления |
| `04_arp.txt` | ARP-таблица | С кем хост общался в своём сегменте — след бокового перемещения |
| `04_dns_hosts.txt` | `resolv.conf`, `hosts` | Подменённый DNS или запись в hosts перенаправляет трафик на инфраструктуру атакующего |
| `04_firewall_*.txt` | правила iptables/nftables | Добавленное разрешающее правило открывает доступ извне |

### 5. Службы

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `05_services_running.txt` | работающие юниты | Незнакомая служба = закрепление с автоперезапуском |
| `05_services_enabled.txt` | автозапуск | Что переживёт перезагрузку |
| `05_timers.txt` | таймеры systemd | **Часто упускаемый вектор.** Современная замена cron; проверяющие про неё забывают, атакующие — нет |

### 6. Планировщик

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `06_crontab_system.txt` | `/etc/crontab`, `/etc/cron.d` | Системные задания |
| `06_crontab_users.txt` | персональные crontab всех пользователей | Самый частый механизм закрепления после SSH-ключей. Требует root для чужих заданий |
| `06_cron_dirs.txt` | содержимое `cron.hourly/daily/...` | Скрипт, положенный в такой каталог, выполняется без записи в crontab |

### 7. Учётные записи

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `07_passwd.txt` | все учётные записи | Поиск записей с UID 0 и созданных вручную |
| `07_group.txt` | группы | Кто добавлен в `sudo`, `wheel`, `docker` (последняя равносильна root) |
| `07_shadow_metadata.txt` | статус пароля **без хешей** | Пустые пароли, даты смены |
| `07_sudoers.txt` | конфигурация sudo | Строка `NOPASSWD: ALL` для обычного пользователя — готовое повышение привилегий |

### 8. SSH

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `08_authorized_keys.txt` | ключи всех пользователей | **Механизм закрепления №1.** Добавленный ключ даёт доступ и после смены пароля. Опция `command=` выполняет команду при каждом подключении |
| `08_sshd_config.txt` | конфигурация сервера | `PermitRootLogin yes`, нестандартный порт, разрешённая парольная аутентификация |

### 9. Журналы

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `09_auth_log.txt` | последние 2000 строк auth.log/secure | Основа анализа аутентификации. Отсюда данные забирает SOC Log Analyzer |
| `09_journal_auth.txt` | journald по sshd/sudo/su | Там, где вместо файлов journald |
| `09_log_files_listing.txt` | список файлов журналов с размерами | **Пустой или обнулённый журнал — сама по себе находка:** заметание следов |

### 10. Закрепление

| Файл | Содержимое | Значение для DFIR |
|---|---|---|
| `10_shell_startup.txt` | `.bashrc`, `.profile` и аналоги | Команда, дописанная в конец, выполняется при каждом входе |
| `10_ld_preload.txt` | `/etc/ld.so.preload` | **На штатной системе файла нет.** Библиотеки отсюда подгружаются в каждый процесс и могут подменять системные вызовы — руткит пользовательского уровня |
| `10_suid_sgid.txt` | файлы с SUID/SGID | SUID-root на бинарнике в `/tmp` или домашнем каталоге — готовый путь к root |
| `10_recent_systemd_units.txt` | юниты, изменённые за 30 дней | Свой юнит = закрепление с автоперезапуском |
| `10_recent_etc_changes.txt` | изменения в `/etc` за 7 дней | Отправная точка временной шкалы инцидента |
| `10_executables_in_tmp.txt` | исполняемые файлы в `/tmp`, `/var/tmp`, `/dev/shm` | Каталоги доступны на запись всем — обычное место полезной нагрузки |
| `10_rc_local.txt` | `rc.local` | Устаревший, но рабочий механизм автозапуска |

### Служебные файлы

| Файл | Назначение |
|---|---|
| `SUMMARY.txt` | Человекочитаемая сводка |
| `findings.json` | Машиночитаемый отчёт для единой CLI набора |
| `00_triage.log` | Журнал сбора: что собрано, что не удалось и почему |
| `MANIFEST.sha256` | Контрольные суммы — доказательство целостности артефактов |

## Проверки

| Проверка | Что ищет | Severity |
|---|---|---|
| Учётные записи с UID 0 | любая запись кроме root с UID 0 | critical |
| Подозрительные записи | служебная запись с оболочкой, пустой пароль, нестандартный дом. каталог | critical / medium / low |
| Слушающие порты | порты типовых средств удалённого управления, службы на `0.0.0.0` | high / info |
| Задания cron | «скачать и выполнить», base64, обратные подключения, ежеминутный запуск | high / medium |
| Ключи SSH | число ключей, опция `command=`, `PermitRootLogin yes` | info / medium |
| Неудачные входы | массовый перебор, **успех с адреса, с которого шёл перебор** | high / critical |
| Процессы | удалённый бинарник, запуск из `/tmp`, маскировка под потоки ядра | high / medium |
| Закрепление | `ld.so.preload`, SUID вне системных каталогов, автозагрузка оболочки | critical / high |

**Проверки — это эвристики, а не доказательства.** Открытый порт 4444 не
означает компрометацию: так мог настроить разработчик. Учётная запись с UID 0
бывает легитимной. Задача проверок — сократить объём ручного разбора, указав,
куда смотреть в первую очередь.

Отсюда два правила оформления находок: у каждой есть **доказательство**
(конкретная строка, а не «что-то подозрительное») и **обоснование**, почему
это признак. Находку без доказательства невозможно проверить.

## Технические решения

### Почему не `set -e`

Обычный совет для Bash — включать `set -e`, чтобы скрипт падал на первой
ошибке. **Для скрипта реагирования это неверно.** Если на хосте нет `ss` или
недоступен `/var/log/secure`, это не повод прервать сбор и потерять все
остальные артефакты. Используется `set -uo pipefail`, а ошибки обрабатываются
явно, каждой командой.

* `set -u` — обращение к неинициализированной переменной считать ошибкой.
  Опечатка в имени переменной иначе молча даёт пустую строку, а в скрипте,
  который ходит по путям файловой системы, пустая строка опасна.
* `set -o pipefail` — код возврата конвейера берётся от упавшего звена, иначе
  `grep … | tail` «успешен» всегда, даже если файла не существует.

### Ловушка `grep -c`

Найдена при первом же прогоне:

```bash
COUNT="$(grep -c 'шаблон' "$FILE" || printf '0')"   # НЕВЕРНО
```

`grep -c` при нуле совпадений **уже печатает `0`** и при этом возвращает код
1 — запасная ветка добавляет второй ноль, переменная становится `"0\n0"`, и
следующее же арифметическое сравнение падает. Правильно:

```bash
COUNT="$(grep -c 'шаблон' "$FILE" 2>/dev/null)" || COUNT=0
```

### Как тестировать скрипт реагирования

Проблема очевидна: чтобы проверить детект руткита, нужна заражённая машина.
Решение — **разделение сбора и анализа**. Проверки читают собранные артефакты
из каталога, а системные файлы — через подменяемые переменные
(`PASSWD_FILE`, `SHADOW_FILE`, `LD_PRELOAD_FILE`). В тестах подставляется
каталог с заготовленными «уликами», и каждая проверка прогоняется на
воспроизводимых данных.

Половина тестов — **контрпримеры**: штатное задание `certbot renew` не должно
давать находку, `postgres` на `127.0.0.1` тоже, штатные SUID-файлы тоже.
Проверка, срабатывающая на чём угодно, бесполезна.

### Формат находок

Находки копятся построчно в JSON Lines и лишь в конце собираются в массив.
Дописать строку в файл — атомарная операция; собирать JSON конкатенацией по
ходу работы значит рисковать испорченным файлом при любом сбое.

## Что рассказать на собеседовании

### «Почему порядок сбора именно такой?»

> Принцип убывающей летучести из RFC 3227. Сначала снимается то, что исчезнет
> при первом изменении состояния: список процессов, сетевые соединения,
> активные сессии. Потом то, что лежит на диске и никуда не денется:
> конфигурации, ключи, задания cron. Если начать с медленного поиска
> SUID-файлов по всей файловой системе, процесс атакующего может успеть
> завершиться, и мы его не увидим.

### «Что вы соберёте, если у вас нет root?»

> Процессы, свои сессии, сетевые соединения без привязки к процессам,
> `/etc/passwd`, свой crontab, конфигурацию SSH, содержимое домашних
> каталогов, доступных на чтение. Не соберу: `/etc/shadow`, чужие crontab,
> `lastb`, журналы аутентификации, правила firewall. Принципиально, что
> скрипт **помечает недоступное явно**, а не выдаёт пустой файл. Пустой отчёт,
> означающий «мы не смогли посмотреть», нельзя путать с «мы посмотрели и
> ничего не нашли».

### «Какие механизмы закрепления вы проверяете и почему именно их?»

> Шесть основных: SSH-ключи в `authorized_keys`, задания cron и таймеры
> systemd, файлы автозагрузки оболочки, свои юниты systemd, SUID-файлы и
> `/etc/ld.so.preload`. Выбор по критерию «переживает перезагрузку и смену
> пароля». Самый недооценённый — `ld.so.preload`: библиотека оттуда
> подгружается в каждый процесс и может подменять системные вызовы, скрывая
> файлы и процессы от штатных утилит. На нормальной системе этого файла
> просто нет, поэтому само его наличие — критическая находка.

### «Как убедиться, что скрипт ничего не сломает?»

> Во-первых, в нём нет ни одной изменяющей команды: только чтение, `find`,
> `ps`, `cat`. Во-вторых, единственная запись — в каталог результатов,
> который задаётся аргументом. В-третьих, в тестах есть проверка-канарейка:
> создаётся временный файл, считается его хеш, прогоняется скрипт, хеш
> сверяется. В-четвёртых, рекомендация запускать с внешнего носителя и писать
> результаты вне исследуемого хоста.

### «Почему выводите JSON, а не только текст?»

> Текст читает человек, JSON читает машина. Этот скрипт — часть набора
> инструментов, и его результаты подхватывает единая CLI-оболочка, которая
> сводит находки от всех трёх инструментов в общий отчёт. Без машиночитаемого
> формата такая интеграция невозможна, и скрипт остался бы вещью в себе.
