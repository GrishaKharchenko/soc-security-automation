# SOC Log Analyzer

> Модуль репозитория [soc-security-automation](../../README.md) · Python · автономный проект

Инструмент поиска атак на учётные записи в логах аутентификации Linux и
Windows. Разбирает разнородные форматы в единую модель событий, применяет
девять правил детектирования, связывает срабатывания в инциденты и
сопоставляет каждое с техниками MITRE ATT&CK.

> **Безопасность тестовых данных.** Логи в `data/` синтетические, созданы
> генератором `data/generate_samples.py`. Адреса — из документационных
> диапазонов RFC 5737, имена вымышлены, реальных систем и настоящей
> вредоносной активности в репозитории нет.

## Архитектура

```
  auth.log ──┐
             ├──► parsers ──► AuthEvent ──► detection ──► Detection ──┐
  *.csv  ────┘   (формат-      (единая      (9 правил)   (находка)    │
  *.json         зависимые)     модель)                                │
                                                                       ▼
                                                          correlate ──► Incident
                                                          (связывание)      │
                                                                            ▼
                                                                    JSON / CSV / консоль
```

**Ключевое решение — единая модель `AuthEvent`.** Linux пишет
`Failed password for invalid user admin from 192.0.2.10`, Windows отдаёт
событие 4625 с полями `TargetUserName` и `IpAddress`. Правила не должны
знать об этой разнице. Вся специфика форматов заперта в парсерах, поэтому:

* правило тестируется списком событий, без файлов на диске;
* добавить источник (Cisco ASA, VPN, Okta) = написать один парсер;
* события из разных источников сводятся в общую хронологию, и корреляция
  видит связь между Linux-хостом и контроллером домена.

## Правила детектирования

| ID | Правило | MITRE | Severity |
|---|---|---|---|
| AUTH-001 | Подбор пароля к учётной записи | T1110.001 (+T1078) | MEDIUM…CRITICAL |
| AUTH-002 | Распределённый подбор с многих адресов | T1110 | MEDIUM…HIGH |
| AUTH-003 | Password spraying | T1110.003 (+T1078) | HIGH…CRITICAL |
| AUTH-004 | Перебор имён учётных записей | T1087 | MEDIUM |
| AUTH-005 | Успешный вход после серии неудач | T1078, T1110.001, T1021 | MEDIUM…CRITICAL |
| AUTH-006 | Неудачные попытки повышения привилегий | T1548.003 | MEDIUM…HIGH |
| AUTH-007 | Блокировка учётных записей | T1531, T1110 | MEDIUM…HIGH |
| AUTH-008 | Вход вне рабочего времени | T1078 | LOW |
| AUTH-009 | Вход с нового источника | T1078 | LOW |

Полный список с обоснованием техник: `python -m log_analyzer rules`.

### Как работает обнаружение brute force

Три идеи, каждая из которых решает конкретную проблему.

**1. Ключ группировки — пара (пользователь, источник).**
Группировка только по пользователю смешала бы забывчивого сотрудника,
у которого не подставился пароль на трёх устройствах, с настоящей атакой.
Группировка только по адресу приняла бы за brute force распылённую атаку,
у которой другая природа и другая техника ATT&CK. Пара даёт точный портрет
подбора пароля к конкретному аккаунту.

**2. Скользящее окно вместо фиксированных отрезков.**
Если считать события по календарным пятиминуткам, атака, попавшая на границу
отрезков, разделится пополам и не превысит порог ни в одной половине.
Скользящее окно проверяет любой промежуток нужной длины. Реализация — два
указателя по отсортированному списку, сложность O(n).

**3. Один всплеск — один алерт.**
Наивное скользящее окно для 50 попыток подряд выдаст 45 почти одинаковых
групп, и аналитик получит 45 алертов вместо одного. Найденный всплеск
поглощается целиком: группа расширяется вперёд, пока разрыв между соседними
событиями не превышает окно.

Severity поднимается, если атакована привилегированная учётная запись, если
скорость превышает 10 попыток в минуту, и становится `CRITICAL`, если за
серией последовал успешный вход с того же адреса.

### Почему spraying — отдельное правило

Политика блокировки считает неудачи **по каждой учётной записи**: пять
промахов — блокировка. Атакующий, который это знает, берёт один-два
вероятных пароля и пробует их по сотне логинов. По каждому аккаунту — две
попытки, порог не превышен, счётчик «неудач на пользователя» молчит.

**Детект brute force такую атаку не увидит принципиально** — он смотрит не
туда. Правило AUTH-003 разворачивает ключ группировки: считает число
различных пользователей на источник и требует, чтобы попыток на каждого было
мало. Второе условие обязательно — без него правило продублирует AUTH-001.

Отдельно исключаются попытки по несуществующим учётным записям: это разведка
имён (T1087, правило AUTH-004), а не распыление пароля.

### Как связываются события

Одна атака порождает несколько срабатываний. Разведка имён, затем подбор,
затем успешный вход, затем попытки sudo — это четыре находки и **один**
инцидент. Аналитику нужна цепочка, а не разрозненные строки, между которыми
он должен сам догадаться о связи.

Ключ связывания — адрес источника, а при его отсутствии имя учётной записи.
Обоснование: подавляющее большинство цепочек в логах аутентификации
разворачивается вокруг одного источника. Учётная запись как запасной ключ
нужна для событий без адреса — sudo и блокировки его не содержат. Находки,
охватывающие много сущностей сразу (массовая блокировка), группируются по
правилу, чтобы инцидент не назывался именем первой попавшейся учётной записи.

Инцидент получает максимальную severity среди своих находок и объединённый
список техник ATT&CK.

**Ограничение, о котором честно стоит помнить:** инцидент, где атакующий
сменил адрес после успешного входа, распадётся на два. Полноценное решение —
граф связей сущностей, где узлы соединяются по любому общему атрибуту.
Для учебного проекта это избыточно, но промышленные системы корреляции
устроены именно так.

## Работа со временем

Классический syslog **не содержит ни года, ни часового пояса**:

```
Aug 18 21:01:00 web01 sshd[1234]: Failed password for root from 192.0.2.10
```

Игнорировать это нельзя: все правила работают с временными окнами, и ошибка
в поясе на три часа развалит корреляцию. Поэтому:

* год берётся из `--year`, из `LOG_DEFAULT_YEAR` или из времени изменения
  файла (не из текущей даты — анализ прошлогоднего архива получил бы будущие
  даты);
* часовой пояс задаётся `--timezone` или `LOG_TIMEZONE`;
* переход через новый год внутри файла отслеживается: если время «прыгнуло»
  назад более чем на полгода, год увеличивается;
* формат ISO 8601 со смещением (современный rsyslog) поддержан и
  предпочтителен — он самодостаточен;
* внутри всё приводится к UTC.

## Что нашёл первый прогон по тестовым данным

Тестовые логи специально содержат не только атаки, но и **контрпримеры** —
легитимное поведение, похожее на атаку. Без них невозможно отличить рабочий
детект от детекта, срабатывающего на что угодно. Первый прогон выявил четыре
проблемы качества:

**1. Ложное срабатывание на забывчивом пользователе.** Сотрудница трижды
ошиблась паролем со своего рабочего места и вошла — правило выдало `CRITICAL`
«вероятная компрометация». Исправлено: если учётная запись уже успешно
входила с этого адреса раньше, находка понижается до `MEDIUM` с низкой
уверенностью. Именно так рассуждает аналитик: знакомый адрес меняет
интерпретацию.

**2. Дублирование техник ATT&CK.** Правило spraying срабатывало на разведке
имён, и одно поведение получало два разных алерта с разными техниками.
Исправлено: попытки по несуществующим учётным записям исключены из AUTH-003.

**3. Инцидент назывался именем первой попавшейся учётной записи.** Массовая
блокировка пяти аккаунтов превращалась в «активность с учётной записи
jsmith». Исправлено: находки с множеством сущностей группируются по правилу.

**4. Пропуск самой важной находки.** Распыление пароля **удалось**, но
правило этого не отметило: успешный вход случился через 134 секунды после
последней неудачи, а проверка искала успех строго внутри всплеска. Между тем
это нормальный ход атаки — сначала прогоняется весь список логинов, потом
атакующий заходит под тем, где пароль подошёл. Исправлено расширением
горизонта поиска.

Все четыре закрыты регрессионными тестами.

## Что рассказать на собеседовании

### «Как работает обнаружение brute force?»

> Считаю неудачные попытки в скользящем окне с группировкой по паре
> «пользователь + адрес источника». Скользящее окно, а не фиксированные
> интервалы — иначе атака на границе интервалов делится пополам и порог не
> превышается. Пара как ключ — потому что группировка только по пользователю
> смешивает забывчивого сотрудника с атакой, а только по адресу — превращает
> в brute force password spraying, у которого другая техника ATT&CK.
> Отдельно решаю проблему шума: 50 попыток подряд должны дать один алерт,
> а не сорок пять, поэтому найденный всплеск поглощается целиком.

### «Чем password spraying отличается и почему нужно отдельное правило?»

> Политика блокировки считает неудачи по каждой учётной записи. Атакующий
> берёт один популярный пароль и пробует его по сотне логинов — по каждому
> аккаунту две попытки, порог не превышен, детект перебора молчит.
> Он **принципиально** не может это увидеть, потому что смотрит на неудачи
> на пользователя, а надо смотреть на число пользователей на источник.
> В тестах у меня есть прямая проверка: на распылении правило AUTH-001
> возвращает пустой список, а AUTH-003 срабатывает.

### «Почему выбрана именно эта техника ATT&CK?»

> У каждой техники в `mitre.py` записано поле `rationale` — какое именно
> наблюдаемое поведение ей соответствует и чем она отличается от соседней.
> Например, перебор несуществующих логинов я отношу к T1087 Account Discovery,
> а не к T1110: цель здесь не подобрать пароль, а выяснить, какие учётные
> записи существуют, потому что система отвечает на валидный и невалидный
> логин по-разному. Это разведка перед атакой, тактика Discovery.
> А успешный вход после серии неудач — это T1078 Valid Accounts, потому что
> с этого момента действия атакующего неотличимы от действий легитимного
> пользователя; сам по себе успешный вход техникой не является, значение
> придаёт контекст.

### «Как связаны события между собой?»

> Одна атака даёт несколько срабатываний: разведка, перебор, успех, sudo.
> Я связываю их по общей сущности — прежде всего по адресу источника, при
> его отсутствии по учётной записи — и собираю в инцидент с максимальной
> severity и объединённым списком техник. Ограничение честно описано в
> README: если атакующий сменил адрес после входа, инцидент распадётся на
> два. Правильное решение — граф связей сущностей, так устроены промышленные
> корреляторы; для учебного проекта я счёл это избыточным.

### «Как вы боретесь с ложными срабатываниями?»

> Три способа. Первый — пороги в конфигурации, а не в коде: у разных команд
> разная толерантность. Второй — разделение severity и confidence: вход в
> три часа ночи может быть критичным по последствиям, но уверенность в нём
> низкая, и смешивать эти оси в один показатель значит терять информацию.
> Третий — контекст: в тестовых данных я специально держу контрпримеры, и
> первый же прогон показал, что сотрудник, трижды ошибшийся паролем на своём
> рабочем месте, получает `CRITICAL`. Добавил проверку, входила ли учётная
> запись с этого адреса раньше; знакомый адрес понижает находку до `MEDIUM`.

### «Почему не разбираете EVTX напрямую?»

> Потому что в реальной работе аналитик почти никогда не держит сырой EVTX:
> события приезжают из SIEM или из `Get-WinEvent | Export-Csv` уже
> разобранными. Поддерживать надо этот вход. Парсинг бинарного формата
