# SOC Automation Toolkit

> Модуль репозитория [soc-security-automation](../../README.md) · Python · объединяет три инструмента

Единая CLI-оболочка над тремя инструментами набора. Запускает их по
отдельности или все сразу, приводит результаты к общему формату и —
главное — **связывает находки разных инструментов по общим сущностям**.

---

## Зачем объединение

Каждый инструмент по отдельности видит свой срез:

| Инструмент | Что он видит | Как это выглядит в одиночку |
|---|---|---|
| IOC Analyzer | «адрес 192.0.2.66 помечен как вредоносный» | рутина: в любом фиде сотни таких |
| SOC Log Analyzer | «с 192.0.2.66 шёл перебор пароля к root» | фоновый шум для сервера в интернете |
| Linux Incident Triage | «на хосте новый SSH-ключ и SUID-файл в /tmp» | возможно, плановая работа админа |

Вместе это **одна атака, доведённая до закрепления**. Пока каждый инструмент
говорит на своём языке, связать их может только человек вручную — а
масштабируется это плохо.

```
$ python -m soc_toolkit run --iocs … --logs … --triage-report …

  ПОДТВЕРЖДЕНО НЕСКОЛЬКИМИ ИНСТРУМЕНТАМИ (наивысший приоритет разбора):
  ▸ ip=192.0.2.66  [CRITICAL]  источники: ioc-analyzer, linux-triage, log-analyzer
      └─ [linux-triage ] Успешный вход с адреса 192.0.2.66, с которого шёл перебор
      └─ [log-analyzer ] Подбор пароля: root с 192.0.2.66
      └─ [ioc-analyzer ] Индикатор 192.0.2.66 — вердикт «malicious»
```

## Архитектура

```
                    ┌──────────────────────────────┐
                    │        soc_toolkit           │
                    │            CLI               │
                    └───────────────┬──────────────┘
                                    │
             ┌──────────────────────┼──────────────────────┐
             ▼                      ▼                      ▼
      ┌────────────┐         ┌────────────┐         ┌────────────┐
      │ IOCAdapter │         │LogsAdapter │         │TriageAdapt.│
      └──────┬─────┘         └──────┬─────┘         └──────┬─────┘
             │ import               │ import               │ subprocess
             ▼                      ▼                      │ или JSON
      ioc_analyzer            log_analyzer            triage.sh
             │                      │                      │
             └──────────┬───────────┴──────────┬───────────┘
                        ▼                      ▼
                  ┌──────────────────────────────┐
                  │      Finding (общая модель)   │
                  └───────────────┬──────────────┘
                                  ▼
                        correlate + escalate
                                  ▼
                       JSON / CSV / консоль
```

**Адаптер** — единственное место, где живёт знание о конкретном инструменте.
Оболочка не зависит ни от одного из них напрямую: добавить четвёртый
инструмент означает написать один адаптер, не трогая ни CLI, ни корреляцию,
ни отчёты.

### Единая модель `Finding`

Три инструмента отвечали на разные вопросы и выдавали разные структуры:
вердикт с risk score, находку правила с severity и техниками ATT&CK, признак
компрометации хоста. Общий знаменатель — что нашли, насколько серьёзно, к
каким сущностям относится и что делать.

Шкала критичности взята из Log Analyzer как самая выразительная. Вердикты
IOC Analyzer переводятся явной таблицей:

| Вердикт IOC Analyzer | Severity набора | Почему |
|---|---|---|
| `malicious` | HIGH (CRITICAL при risk score ≥ 85) | подтверждённая угроза |
| `suspicious` | MEDIUM | возможен false positive |
| `unknown` | **LOW, не INFO** | VT не знает индикатор — для свежей инфраструктуры ожидаемо и слегка подозрительно |
| `error` | **LOW, не INFO** | не проверили ≠ безопасно; должно остаться на виду |
| `clean` / `skipped` | INFO | по умолчанию не попадают в отчёт |

### Связывание сущностей

Инструменты называли одно и то же по-разному: Log Analyzer хранил адрес в
`entities["source_ip"]`, IOC Analyzer — в `entities["ip"]`. Пока имена
расходятся, корреляция невозможна. Приведение к общему словарю (`ip`,
`domain`, `url`, `hash`, `username`, `hostname`) и есть цена объединения.

Связывание по `hostname` по умолчанию **выключено**: в рамках одного прогона
имя хоста одинаково у всех находок триажа и склеило бы их в одну бессмысленную
группу.

### Эскалация при подтверждении

Находка, подтверждённая **независимо** несколькими инструментами, повышается
на один уровень критичности — но не выше HIGH. Независимое подтверждение —
сильнейший из доступных сигналов: адрес, который одновременно числится
вредоносным в Threat Intelligence и фигурирует в логах как источник перебора,
это уже не гипотеза. Ограничение до HIGH нужно, чтобы не обесценить уровень
CRITICAL. Отключается флагом `--no-escalate`.

## Установка и запуск

Оболочке нужны зависимости всех модулей. Проще всего — одно окружение:

```bash
cd projects/soc-toolkit
python -m venv .venv
source .venv/bin/activate                 # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -r ../ioc-analyzer/requirements.txt
pip install -r ../log-analyzer/requirements.txt
```

Проверка окружения:

```bash
python -m soc_toolkit status
```

```
МОДУЛИ НАБОРА
--------------------------------------------------------------
  IOC Analyzer (Python)              доступен
  SOC Log Analyzer (Python)          доступен
  Linux Incident Triage (Bash)       доступен
--------------------------------------------------------------
  Запуск сбора триажа из оболочки: нет (нужен Linux или WSL)
  Импорт готового отчёта триажа:   да, на любой платформе
```

### Команды

```bash
# индикаторы (ключ VirusTotal берётся из projects/ioc-analyzer/.env)
python -m soc_toolkit ioc -i ../ioc-analyzer/data/sample_iocs.txt
python -m soc_toolkit ioc -i feed.csv --offline --limit 20

# логи аутентификации
python -m soc_toolkit logs -i ../log-analyzer/data/auth.log --year 2026
python -m soc_toolkit logs -i auth.log security.csv --timezone Europe/Moscow

# триаж: импорт готового отчёта (работает везде, включая Windows)
python -m soc_toolkit triage --report ../linux-triage/samples/findings.json
# триаж: живой сбор (только Linux/WSL)
sudo python -m soc_toolkit triage --run --triage-output /mnt/usb

# всё сразу с общей корреляцией — главный сценарий
python -m soc_toolkit run \
    --iocs samples/incident_iocs.txt --offline --include-clean \
    --logs ../log-analyzer/data/auth.log --year 2026 \
    --triage-report ../linux-triage/samples/findings.json
```

Общие параметры: `-o/--output-dir`, `-f/--format {json,csv,both,none}`,
`--min-severity`, `--no-escalate`, `-q/--quiet`, `--log-level`.

| Код возврата | Значение |
|---|---|
| 0 | находок нет |
| 1 | есть находки |
| 2 | есть критические находки |
| 3 | ошибка запуска |

### Демонстрационный набор данных

`samples/incident_iocs.txt` содержит те же адреса, что фигурируют в логах
Log Analyzer и в отчёте триажа. Совпадение сделано намеренно — оно
демонстрирует кросс-корреляцию без реального инцидента. Все адреса из
документационных диапазонов RFC 5737.

## Конфигурация

**У каждого модуля свой `.env`** — это осознанное решение. Заставлять модули
читать общий конфиг означало бы сломать их автономность, а она нужна: каждый
инструмент должен оставаться пригодным к самостоятельному использованию.

| Файл | Что задаёт |
|---|---|
| `projects/ioc-analyzer/.env` | ключ VirusTotal, лимиты API, пороги вердикта |
| `projects/log-analyzer/.env` | пороги детектирования, часовой пояс |
| `projects/soc-toolkit/.env` | каталог отчётов, логирование, эскалация |

## Известные компромиссы

Честный список — вопросы по нему на собеседовании неизбежны, и лучше назвать
их самому.

**1. Импорт соседних проектов через `sys.path`.** Промышленный путь — оформить
каждый проект как устанавливаемый пакет и объявить зависимостями. Здесь
выбран более простой вариант ради запуска без установки; весь «магический»
код сосредоточен в одном явном месте — `bootstrap.py`. Ограничение: при
переносе оболочки отдельно от репозитория импорт сломается.

**2. Извлечение сущностей триажа регулярными выражениями.** Bash-скрипт
оперирует текстом находки, а не структурированными полями, поэтому адреса и
учётные записи вытаскиваются из текста. Правильнее было бы, чтобы скрипт сам
заполнял поле `entities`; разбор текста зависит от формулировок и сломается
при их изменении.

**3. Индикаторам не приписываются техники ATT&CK.** Вредоносный хеш сам по
себе не соответствует никакой технике: техника описывает поведение, а не
артефакт. Приписать индикатору, скажем, T1071 было бы догадкой, выдаваемой за
факт. Техники приходят из Log Analyzer, где выведены из наблюдаемого поведения.

**4. Корреляция — по точному совпадению значений.** Адрес из подсети атакующего,
отличающийся последним октетом, связан не будет. Промышленные корреляторы
строят граф сущностей и учитывают подсети, домены второго уровня и временную
близость.

## Тесты

```bash
python -m pytest              # 48 тестов
```

| Файл | Что проверяет |
|---|---|
| `test_models_and_correlation.py` | стабильность идентификаторов, группировка, эскалация, отсев мусорных ключей |
| `test_adapters.py` | перевод вердиктов, полнота таблицы соответствия, извлечение сущностей, обработка битых отчётов |
| `test_cli_and_reporting.py` | все команды, сквозная корреляция трёх инструментов, изоляция сбоя модуля |

Отдельно стоит отметить тест `test_every_verdict_has_a_severity`: он
перебирает **все** вердикты IOC Analyzer и требует, чтобы каждый был
сопоставлен с критичностью. Если в модуле появится новый вердикт, тест
упадёт, а не позволит ему молча провалиться в INFO — типичная ошибка
интеграции.

## Что рассказать на собеседовании

### «Зачем объединять инструменты, если каждый работает?»

> Потому что аналитик работает с инцидентом, а не с инструментами. По
> отдельности вредоносный адрес в фиде — рутина, перебор паролей из интернета —
> фоновый шум, новый SSH-ключ — возможно, работа админа. Вместе это одна атака.
> Оболочка приводит результаты к общей модели и связывает их по сущностям, а
> подтверждение из нескольких независимых источников повышает приоритет
> разбора. Это ровно то, чем занимается корреляционный движок SIEM, только в
> миниатюре.

### «Как вы свели три разных формата к одному?»

> Определил модель `Finding` с полями «что нашли, насколько серьёзно, к каким
> сущностям относится, что делать» и написал по адаптеру на инструмент. Вся
> специфика заперта в адаптерах, поэтому CLI, корреляция и отчёты не знают ни
> об одном инструменте. Самая содержательная часть — таблица перевода
> вердиктов: например, «ошибка проверки» и «VT не знает индикатор» я
> сознательно кладу в LOW, а не в INFO, чтобы они не терялись — не проверили
> не равно безопасно.

### «Что будет, если один модуль упадёт?»

> Прогон продолжится. Каждый модуль вызывается через обёртку, которая ловит и
> известные ошибки адаптера, и любое непредвиденное исключение — модули
> разрабатывались независимо, и оболочка не может знать полный перечень их
> ошибок. Сбой попадает в список `failed_modules` в отчёте и в stderr, а код
> возврата не может быть нулевым при частичном сбое: иначе неполный результат
> выглядел бы как чистый. На это есть отдельный тест.

### «Как интегрирован Bash-скрипт?»

> Двумя способами. Первый — запуск через `subprocess` с разбором созданного
> `findings.json`. Второй, и он основной, — импорт готового отчёта: триаж
> запускается на исследуемом хосте, а разбор ведётся в другом месте, часто на
> другой платформе. Именно поэтому Bash-скрипт с самого начала пишет
> машиночитаемый отчёт, а не только текст. На Windows режим запуска
> недоступен, и оболочка говорит об этом прямо, предлагая импорт.

### «Что бы вы сделали иначе?»

> Три вещи. Оформил бы модули как устанавливаемые пакеты вместо правки
> `sys.path`. Заставил бы Bash-скрипт заполнять структурированное поле
> `entities` вместо разбора текста регулярками на стороне оболочки. И заменил
> бы корреляцию по точному совпадению на граф сущностей с учётом подсетей и
> временной близости. Все три компромисса описаны в README — я предпочитаю
> называть их сам, а не делать вид, что их нет.
